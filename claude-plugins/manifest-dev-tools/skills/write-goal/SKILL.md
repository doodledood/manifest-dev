name: write-goal
description: 'Write one standalone goal defining what done means, in at most 4,000 characters, from a Manifest, a figure-out read, a Ticket, a handoff, a plain request or several of them. Use when the user wants to turn this work into a goal, or paste it into a goal field with no file reference behind it.'
argument-hint: '<Manifest, figure-out read, Ticket, handoff or request: a path or inline text>'
user-invocable: true
---

Turn the supplied sources into one standalone goal of at most 4,000 characters. The goal replaces them: the agent that works from it has none of the sources and none of this conversation, so an obligation the goal drops is gone and a requirement it invents becomes binding.

**Sources.** A Manifest — the specification of what to deliver, what counts as done, and the constraints that hold throughout; a figure-out read — a named conclusion with its evidence and what would overturn it, in the conversation or in its log file; a Ticket; a handoff; a plain request; or several of them together. Use the sources identified in the request or conversation; ask which one if the target is missing or ambiguous. Read all of them and the references needed to understand their intent and requirements. Apply explicit user amendments, distinguishing settled decisions from suggestions still under discussion.

What each source owes:
- **A Manifest:** every Acceptance Criterion and Global Invariant with its pass condition — the threshold, check command, artifact or qualitative bar that decides it, wherever in the gate it is stated, the why included. Process Guidance and the Initial Approach advise: carry a method only where a gate binds it.
- **A read:** its conclusion, and what it says will be built and how that will be checked. Each branch it ruled out is an exclusion the goal states. Its evidence, rival explanations, overturn conditions and offers the user did not accept are grounds, not requirements.
- **Any other source:** its settled decisions. Suggestions still under discussion owe nothing.

**Test for gaps before listing.** The sources must settle four things:
1. The finished outcome.
2. A done check that a reader of the goal alone could settle as done or not done.
3. The limits: scope and exclusions.
4. Where the work stops. A source settles this when its done check is the end, or when it names the stop. It is still a gap when the work would reach an act that cannot be undone or needs someone's approval — merging, deploying, sending, spending — and the source does not say whether to take it: a source that ends at a pull request without saying whether to merge it leaves the stop open.

Fill each gap or contradiction that would materially change the goal before drafting; never fill one by invention. A gap that is one clear question, ask the user directly: one ask at a time, each settled by one short answer, and only about the open items above. A gap that needs investigation, or that cannot yet be put as one clear question, invoke the figure-out skill on: give it the open items above as its assignment — settle these for a goal and return the read — and add the read it returns to the sources, then test again. Where the figure-out skill is not available, say so and ask the gap as a question, or stop without a goal.

**List what the goal owes before drafting.** Write down every obligation the sources owe, as above, and every scope limit, exclusion, stopping limit and approval boundary they state. Drop what a user amendment removed. Requirements that share one check may become one only while each of their conditions survives. When the list cannot fit in 4,000 characters without dropping or weakening an item, ask the user which to cut before drafting.

**Draft from the list.** Open with the finished outcome, then state each listed item as a requirement in plain language, with no IDs, workflow jargon, pointer to a source or another document, or step that depends on the workflow that produced a source, such as a Manifest's execution loop. Keep the purpose and rationale that guide interpretation or a trade-off, and examples that define a boundary; keep assumptions qualified. Make completion rest on the listed checks passing on observed results; concrete check commands, named skills and artifact names may define success, each kept by the name the sources give it. Leave execution strategy to the agent, and where the goal keeps advice to guide interpretation — a method, plan or suggestion the sources do not bind — mark it as a suggestion the agent may depart from. Add no metric, budget, reporting format, review step or execution policy that neither the sources nor the user specified, and omit policy the known destination already supplies. Count the goal text programmatically, spaces and punctuation included, and revise until it is at most 4,000 characters; the ceiling is not a target.

**Have it read cold.** Give one fresh context the goal alone, with this file's path as the standard a goal is held to — it reviews, drafting nothing — and ask what the goal would have it build, what limits it sets, and how it would decide it is done. Then give it the sources as text — a Manifest's file, a read's text and its log path, and for a source that lives only in the conversation the user's settling messages quoted — with the user's amendments and your list, and ask it to work out from the sources what the goal owes, treating your list as a claim to check and the sources as the reference rather than the subject of review. Ask it to report each obligation dropped or weakened, each requirement the sources do not state, each piece of advice — a method, plan or suggestion the sources do not bind — stated as a requirement, any removed or superseded scope the goal revives, any reference to a source or its IDs, each condition a reader of the goal alone could not settle as done or not done where the sources settle it, and, for each check the sources name, a plausible wrong result the goal would let pass that the check itself would catch. Where no Manifest is among the sources, nobody has yet reviewed the goal as a contract, so also ask it for conditions that cannot all hold together within the stated scope, and for holes: a requirement the goal states that no check in it settles, so work missing it passes every check, or a check that already passes on the current state while the outcome is missing. A requirement a reader can settle directly, by running a command the goal names and reading its output, is settled. Settle every finding in one pass: fix it, or reject it with its reason, then count the goal again. A finding the sources cannot settle is a gap: fill it as above, never by invention. A fix that would take the goal past 4,000 characters is a cut for the user: ask which item to shorten or drop. No second review follows. Where no isolated context is available, run the same two readings yourself, goal first.

Return the goal as one paragraph inside a single plain-text code fence. Below the fence, add one short note only when a finding was rejected, naming it and why, or the review was self-graded; otherwise return the fence alone. This invocation drafts text only: it does not edit a source, set a running goal or begin the work it describes.
