## Assessment: Good with Minor Issues

I applied your team's rule that every prompt starts with a `ROLE:` line naming the persona. The `ROLE: release-notes writer` line meets it, so it gets no finding, even though the general principles would otherwise question a persona line.

**Strengths** — keep these:
- Almost every line is a decision only your team could make: the three groups, one past-tense line per PR, a link on each line, and skipping PRs labelled `no-release-notes`. None of it is something the model could work out alone.
- The empty case ends on something the run can check: "say so in one line and stop."
- It's short and states the goal directly. Nothing in it is padding.

**Issues**:

| Issue | Severity | Fix |
|-------|----------|-----|
| The command is given as *the* way to find PRs, and it is wrong in two ways. First, `gh pr list` returns only 30 results by default, so a release with more than 30 merged PRs silently loses the rest. Second, `merged:>=<tag date>` only works to the day, so PRs merged on the tag's date but *before* the tag get listed again, even though they already shipped in the last release. | High | Describe the goal and let the model pick the tool: "every PR merged after the last tag was created." If you want to keep the command, add `--limit` with a high value and tell the run to drop PRs whose merge commit the tag already contains. |
| "If there are no merged PRs" doesn't say what happens when PRs were merged but every one is labelled `no-release-notes`. The run may then produce empty group headings instead of the one-line message. | Medium | Make the condition "if no PRs remain after exclusions." |

**Priority**: fix how PRs are collected first. As written, a big release loses PRs without any warning, and any release cut on the same day as the previous tag repeats old entries.
