**What it fixes:** the club can't give a member more time on a book. `overdue` keeps flagging people who were actually allowed to keep the book longer, and nothing limits how often a loan gets extended.

**What it covers, in order:**
1. **A way to test the CLI.** The project has no tests and no test runner yet, so this comes first. It's a small helper that runs the real CLI in a temporary folder, plus a short list of each command and how to check it. It only covers `renew` and `overdue`.
2. **`overdue`.** It's currently a stub that only prints its own name, so it has to be built for "uses the renewed due date" to mean anything. `checkout`, `return` and `export` are stubs too, and I left them alone: tests write the loans file directly.
3. **`renew --book X`.** It extends the loan by one loan period, records when it happened, and refuses a third renewal. When it refuses, it prints a clear error and leaves the file exactly as it was.
4. **Docs.** A decision record explaining the file format, plus definitions of "Renewal" and "Loan period" in the glossary (`CONTEXT.md`).

**The mixed-version problem:** decisions you may want to overrule.
- **Where the renewed date goes:** the spec writes it into the loan's existing `due` field and adds the renewal history as a new list beside it. A laptop that hasn't upgraded still reads `due`, so its overdue report stays correct during the rollout. The other option was to leave `due` alone and work out the real date from the number of renewals. That keeps the original date in place, but old laptops would flag renewed loans as overdue until they upgrade.
- **Renewing an overdue loan is allowed.** You only stated the two-renewal cap, so I didn't add a second rule.
- **Safety rules:** the format may only gain fields, never rename or remove them. The new version keeps any field it doesn't recognise. Saves replace the whole file in one step, so the synced folder never picks up a half-written file.

**Things I had to settle because nothing in the repo defines them:**
- **Loan format:** the repo has no loans file and no defined record shape, so I assumed a loan has a member, book, checkout date, due date and return date. If the version on the laptops uses different field names, those take over.
- **Loan period:** it comes from the loan's own dates (original due date minus checkout date), so there's no new setting to configure.

**Known gaps, written down rather than solved:**
- **Two laptops at once:** if two laptops renew at nearly the same moment, the sync keeps only one copy. A renewal can be lost, or a loan can go over the cap. Fixing that would need locking, which you ruled out.
- **Old laptops rewriting the file:** a laptop that hasn't upgraded might drop the renewal history when it saves, depending on how that older code works. The renewed due date survives either way.

**How it's checked:** `python -m unittest discover -s tests` must pass, with tests built from hand-worked dates. One test renews a loan and confirms `overdue` stops listing it. There are also code-review checks and a check that the work stayed within scope.
