**The problem:** agents run the same few ticket searches all day and set up every filter by hand each time. Nothing is built yet; this is only the plan.

**The plan:** the three deliverables you named, in that order.
1. **Model and migration.** A `SavedSearch` with an owner, a name, the filters and a created date. The filters are stored in the same format the existing ticket search already uses. That way, running a saved search just means applying those filters. A test checks that a saved search gives back exactly the same tickets as typing the filters by hand. This is the riskiest part, so it's checked first.
2. **REST endpoints.** Create, list and delete, each limited to the logged-in agent. They're tested over HTTP with two different agents, and they follow the conventions of your existing ticket endpoints.
3. **Sidebar.** A "Saved searches" section in the sidebar and a "Save search" button on the ticket search view. Clicking a saved search runs it, and deleting asks you to confirm first. It covers the empty, loading and error states, the 50 limit and long names, and it should look like the rest of the admin.

**The rules that must hold:**
- Agents can't see or delete each other's saved searches. If one agent tries to delete another's, they get "not found", so the response doesn't reveal that it exists.
- An agent can have at most 50 saved searches. The 51st save is refused with a clear message, and the check still holds if two saves arrive at the same moment.
- There's no sharing and no editing. Rename or change requests are rejected.
- Existing ticket search behaves exactly as before.
- The migration only adds a new table and can be rolled back.
- All your existing tests and linters pass.
- One full browser run has to pass: save a search, click it to rerun it, delete it, then log in as a second agent and confirm they see none of the first agent's searches.

**Decisions I made that you may want to change:**
- **Deliverables by layer:** I kept the split by layer you asked for. The alternative was splitting by feature (save-and-run end to end, then delete). The full browser run catches problems in how the three parts connect, but only once all three are built.
- **Names:** must be unique for each agent and at most 100 characters.
- **Sidebar order:** alphabetical.
- **Deleted agents:** if an agent's account is deleted, their saved searches go with it.
- **Out-of-date filters:** a saved search that uses a tag that was later deleted behaves however the existing search handles that.

**Assumptions:** because I couldn't see the repo, I assumed:
- the backend uses Django REST Framework;
- the frontend is TypeScript React;
- test suites already exist.
